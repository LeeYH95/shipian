# GitHub Product Launch

把代码、真实产品能力和宣传材料组织成同一套可验证的交付物。复用项目已有品牌，默认使用用户语言；不要擅自重命名产品或更换已确认的图标。

## 1. 定位发布对象

读取项目说明、许可、Git 状态、远程地址、构建入口和已有发布材料。先只读检查认证，不输出凭据。区分工作区、可发布源码与本地运行数据。

确认仓库所有者、名称、可见性和发布范围；已有答案直接沿用。必要信息缺失时集中询问，同时继续准备不依赖答案的本地材料。用户只要素材时不创建或修改远程仓库。

对二次开发核对上游代码与品牌各自的许可，保留作者声明及来源。不要把上游的签名、平台支持或功能当成本项目已验证的能力。

## 2. 建立事实与素材清单

按 [交付清单与格式](references/deliverables.md) 在输出目录建立 `launch-manifest.json`。每条产品承诺记录证据文件，每项素材记录来源、授权状态与用途。

优先复用安全的真实界面；重新采集时使用虚构数据或独立演示配置。截图属于产品证据，禁止用生成图冒充已实现界面。生成背景或装饰可以使用，但不改写产品功能。

生成材料前先写出：产品给谁用、解决什么问题、核心动作顺序和当前限制。把已确认事实、建议文案和未验证能力分开。

## 3. 制作一套能看懂的材料

按项目复杂度选择产物，不机械增加数量：

- README：一句价值主张 → 真实效果 → 核心工作流 → 安装与开始 → 数据及限制 → 构建与参与 → 来源许可。
- 首屏 Banner 与社交预览：产品名、一个清晰结果、真实主界面；复用品牌颜色、字体与图标。
- 功能配图：一张图讲一个场景；保留能理解功能的界面上下文，避免把所有功能挤进首屏。
- 介绍视频：先按 [视频说明](references/video.md) 写分镜和字幕，再调用可用制作能力；导出可播放文件、封面和源工程。只有分镜或动画网页时必须说明尚未交付视频。
- 发布说明：About、Topics、短介绍、Release 文案、已知限制与下载入口。地址尚未确定时保留本地材料，发布时统一替换并检查。

不虚构用户量、性能数据、推荐语、平台支持或公证状态。宣传文案可以有态度，具体功能和数字必须能回到证据。

## 4. 校验并修复

用宿主已检测到的 Python 3.10+ 运行：

```sh
python3 scripts/check_launch.py --root <发布目录> --manifest launch-manifest.json --report <报告路径>
```

检查器负责相对路径、素材尺寸、来源字段、README 链接及常见密钥和个人路径规则；不能证明不存在秘密，也不代替视觉审查。存在 Git 历史时另用可用的历史密钥扫描器。

打开实际导出的图片及视频，检查文字清晰度、裁切、功能真实性、字幕停留和声音。核验安装/运行与源码构建；不把成功编译当作完整体验验收。修复必要问题，保留可用中间产物。

## 5. 发布并核对远程结果

按 [发布与恢复](references/publishing.md) 执行用户已经授权的外部操作。先检查远程是否存在及是否匹配，不覆盖其他项目，不把上游仓库当作上传目标。

使用经过检查的文件白名单提交，不直接上传整个工作区。源码、文档及合理大小的宣传素材进仓库，二进制安装包进入 Release。鉴权失败时停止远程操作，继续完成本地包并说明恢复入口；不索取或记录明文 Token。

发布后读取远程仓库，检查默认分支、README、素材路径、Release 下载和可见性。只有远程结果已核对才声称上传完成。

## 交付

报告仓库/Release 地址、素材与源工程位置、实际校验、兼容边界及未完成项。已有可用图标和数据布局保持不变；后续增量运行复用清单和现有产物，避免重复创建仓库或 Release。
